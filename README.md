# ПИД · Учёт кабеля

Пилотная система суточного учёта демонтажа кабеля. Единый интерфейс — Telegram Mini App.
Бот доставляет запросы и общую сводку; числа в чате не распознаются.

## Текущий результат

- Рабочий проверочный стенд с постоянным хранилищем и тестовыми ролями.
- Формы копки, намотки, отправки и приёмки; проверка перед подтверждением.
- Выходной, простой, текст и аудиопояснение.
- Просмотр ПИД, расчётных остатков, рейсов, первичных записей и версий.
- Администрирование сотрудников, закреплений, типов, замеров и начальных данных.
- Корректировка по проверенному фактическому остатку; контроль поздних изменений.
- Настоящий XLSX: отправки, приёмки, изменения, описание формата.
- Подготовлены проверка Telegram initData, webhook, планировщик, bootstrap владельца.
- Проверочный режим физически отделён от production пространством данных. В нём не отправляются сообщения Telegram.

## Архитектура

React + TypeScript, Vinext / Cloudflare Worker, D1 (SQLite), R2 (аудио).
API и формы используют общий проверяемый модуль lib/domain.ts.
Подтверждённые документы и все версии хранятся в append-only таблице documents.
Один рейс содержит отправку и приёмку в одном агрегате: обновление атомарно.
Документ имеет неизменяемый ID, оптимистическую версию и ключ повтора запроса.
Нет отдельного ввода в чате или второй модели расчётов.

APP_MODE=demo: приватный доступ владельца через Sites; переключение тестовых сотрудников.
APP_MODE=production: авторизация подписанным Telegram initData, доступ только по внесённым Telegram ID. Переключателя ролей нет.
Приватный адрес проверочного стенда не является готовым публичным Telegram webhook.

## Проверка и сборка

- npm run install:ci — установка зафиксированных зависимостей.
- npm test — предметные проверки и реальные API-обработчики на SQLite без сетевых вызовов.
- npx tsc --noEmit — проверка типов.
- npm run build — сборка Worker и интерфейса.
- npm run db:generate — миграция после изменения схемы.
- scripts/telegram-setup.mjs — на целевом хосте настраивает webhook и кнопку приложения из окружения; не запускается автоматически.

## Перед рабочим пилотом

1. Проверить формы с собственником, прорабом и кладовщиком.
2. Выбрать рабочее размещение с публичным HTTPS для Telegram. Приватный Sites-стенд требует входа ChatGPT и не подходит для сотрудников без этого доступа.
3. Создать отдельную production БД; применить миграции. Тестовые документы не переносить.
4. Внести проверенный числовой Telegram ID администратора (scripts/bootstrap-production.mjs генерирует SQL для отдельного импорта).
5. Внести сотрудников, роли, закрепления, ПИД, типы, начальные данные и контрольные замеры.
6. Указать runtime-секреты согласно .env.example. BOT_ENABLED включать только после проверки адреса и списка получателей.
7. Подключить webhook и минутный вызов POST /api/scheduler с защищённым секретом либо scheduled handler на Worker.
8. Указать ID общей группы; добавить туда бота. Сотрудники должны самостоятельно открыть бота через /start.
9. Проверить реальные 19:00 / 20:00 / 21:00 Asia/Krasnoyarsk, резервное копирование и восстановление.

Не включать в репозиторий токены, .env, базы, аудио и файлы с реальными персональными данными.

## Практические ограничения пилота

- Реальные Telegram-рассылки на стенде отключены, webhook не менялся.
- Ведомость катушек сохраняется для разбирательств; отдельного вечного реестра катушек нет.
- ПИД и дата уже созданного отчёта закреплены за записью. Массы и объёмы исправляются с историей.
- При принятом рейсе масса отправки может быть исправлена с сохранением фактической приёмки. Изменение состава и перенос принятого рейса требуют дополнительного согласованного сценария совместного исправления; сейчас запрещены, чтобы не разрушить связи.
- Черновик формы хранится на устройстве; подтверждённые данные — в БД. Перенос черновиков между устройствами пока не включён.
- API выгрузки реализован; адаптер загрузки документов 1С ещё не реализован.
- Массовый реестр пока читается целиком; это пилотная архитектура. До масштабирования нужны серверные страницы и индексы под фактический объём.
- Сбой доставки Telegram с неизвестным результатом не повторяется автоматически; остаётся статус uncertain, чтобы не дублировать сообщения.
- Первоначальная проверка автоматическая и расчётная; визуальная приёмка на телефонах и реальный пилот ещё впереди.
