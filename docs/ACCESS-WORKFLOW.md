# Регистрация и доступ TG / WEB

Доступ определяется по Telegram ID из подписанных данных Telegram и правам записи сотрудника. ФИО из заявки — только комментарий, совпадение имён не проверяется.

## Пользователь

1. Старт → ОТКРЫТЬ УЧЁТ.
2. Известная активная запись открывает учёт. Неизвестная предлагает запрос: Да / Нет.
3. Да сохраняет черновик по ID. При доступном query_id Telegram показывает сообщение от пользователя «Запрашиваю доступ к учёту». Бот спрашивает, как представить пользователя.
4. Ответ одним сообщением переводит заявку в рассмотрение без дополнительного подтверждения имени.
5. До решения показано ожидание. После решения — предоставление доступа или отказ. Отключённая запись не может зарегистрироваться заново.
6. При запуске, не предоставляющем query_id, доступен переход в чат /start access.

## Администратор

Настройки → Доступ TG / WEB: выбрать получателя заявок из действующих администраторов. Пока получатель не выбран или отключён, используется один действующий администратор (по идентификатору сотрудника); назначение сохраняется и видно в настройках.

Уведомление содержит комментарий и ID, кнопки «Рассмотреть» / «Отказать». Рассмотреть открывает настройки доступа в TG. Администратор выбирает существующего сотрудника либо самостоятельно вводит имя новой записи, затем явно выбирает роль: наблюдатель, сотрудник по складам/заданиям, администратор. «Предоставить доступ» атомарно сохраняет привязку и права. Объекты и функции сотрудника назначаются существующими настройками.

## Хранение и доставка

operational_access_requests — текущая заявка по уникальному Telegram ID; name сохраняется как комментарий для совместимости с существующей БД.
operational_access_history — история переходов, комментарий, решение и автор. Прежние заявки копируются в историю миграцией.
operational_identities — связь ID с сотрудником и права.
operational_access_settings — получатель заявок.
operational_access_outbox — очередь уведомлений, созданная в одной транзакции с изменением состояния. Ошибка Telegram не отменяет решение. Повторная отправка после временного сбоя; при неизвестном результате внешней отправки возможно повторное уведомление, но не повторная выдача доступа.

## Проверки

Локальные тесты диалога: одинаковый /start, профиль без фамилии, комментарий из одного слова, ожидание после отправки, защита старой кнопки одобрения, запрет решения для обычного сотрудника.
PostgreSQL CI: пустой черновик, повторный запрос, явная роль, имя администратора вместо комментария, одинаковые имена разных ID, повторное/одновременное решение, история отказа, TG/WEB права, отключение, повтор доставки, неизменность учётных документов.

Проверка реального диалога в клиентах Telegram требуется отдельно от серверных тестов.
