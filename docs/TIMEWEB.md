# Запуск в Timeweb Cloud

Репозиторий: https://github.com/SERFROLL/RSSdemontage.
Проект Timeweb: «Демонтаж кабеля». Приложение разворачивается через App Platform / Dockerfile.

## Как устроены обновления

Изменения попадают в `main`. GitHub Actions проверяет расчёты, SQLite API, PostgreSQL API,
повторные миграции, S3-адаптер, типы, сборку Cloudflare и Docker-контейнер для Timeweb.
Контейнер проверяется с реальной PostgreSQL до и после перезапуска, включая Telegram-вход
и отказ при поддельных заголовках проверочного стенда. После успеха ветка `release`
перемещается на проверенный коммит без принудительной перезаписи истории.

В Timeweb нужно выбрать репозиторий через подключённый аккаунт GitHub, ветку **release**
и включить «Сборка по последнему выполненному коммиту». Подключение только по URL
не заменяет интеграцию GitHub, необходимую для автоматических обновлений.
Приложение `RSSdemontage` создано в Timeweb и связано с веткой `release` через интеграцию GitHub.
После изменения настроек окружения панель предлагает отдельную пересборку приложения.

## Ресурсы

- App Platform: Dockerfile в корне, порт 8080, проверка `/api/health`.
- PostgreSQL 18 в той же приватной сети, ежедневные резервные копии.
- Закрытое хранилище S3 для аудио. Файлы выдаются только через API после проверки роли.

База и аудио не входят в Docker-образ. Повторная сборка их не удаляет.
Проверка `/api/health` задаётся в панели Timeweb. Dockerfile не содержит `HEALTHCHECK`,
который переопределял бы проверку платформы. При старте сервер также проверяет этот
адрес локально и пишет HTTP-статус в журнал без учётных данных.
На старте сервер применяет только новые миграции PostgreSQL из `server/migrations`;
уже применённые файлы проверяются по контрольной сумме и не должны редактироваться.
Действующая Cloudflare-сборка и миграции D1 остаются отдельным вариантом запуска.

## Настройки приложения

В переменных Timeweb заполнить ключи из `.env.timeweb.example`:

1. `DATABASE_URL`: данные подключения PostgreSQL, выданные панелью, с именем рабочей базы.
   Для выбранной приватной сети Timeweb используется `DATABASE_SSL=false`: провайдер
   не предоставляет TLS на приватном адресе управляемой базы. Публичный IP базы не включён.
   Для подключения с TLS используется `DATABASE_SSL=true`; при необходимости добавить
   корневой сертификат в `DATABASE_CA_CERT`. Проверка сертификата при TLS не отключается.
2. `ADMIN_TELEGRAM_ID`: подтверждённый владельцем ID. На пустой базе создаётся администратор.
   Повторные старты не создают дубликатов и не меняют существующие права.
3. `TELEGRAM_BOT_TOKEN`: секрет бота `rsskablebot`, только в настройках хостинга.
4. `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`:
   значения из панели закрытого бакета. Используется адрес сервиса S3, а не публичная ссылка файла.
5. `MINI_APP_URL`: постоянный HTTPS-адрес приложения после выдачи домена Timeweb.
   Он также определяет доверенный адрес обратного прокси для проверки источника запросов.
6. `APP_MODE=production`, `BOT_ENABLED=false` на первоначальном запуске.

Не помещать рабочие значения в GitHub, Dockerfile или аргументы сборки.
Для дальнейшего включения рассылок нужны `TELEGRAM_WEBHOOK_SECRET`, `SCHEDULER_SECRET`
и `SUMMARY_CHAT_ID`. При `BOT_ENABLED=true` сервер выполняет планировщик раз в минуту;
учёт уведомлений в PostgreSQL защищает от повторной отправки между перезапусками и репликами.
Webhook и меню бота настраиваются отдельно после проверки адреса и участников.

## Проверка и восстановление

`/api/health` проверяет подключение и наличие таблицы, не возвращая рабочие данные.
`/api/state` без подписанных данных Telegram должен отвечать 401.
Сначала проверить вход администратора через Telegram, создать пилотный ПИД и сотрудников,
затем проверить запись/чтение и аудио. Резервную копию необходимо проверить восстановлением
в отдельную базу перед вводом рабочих данных.

Откат кода: выбрать ранее проверенный коммит в Timeweb. Базу не откатывать автоматически:
новые записи и история должны сохраняться. Изменения схемы проектировать совместимыми
с предыдущей версией; для несовместимых миграций нужен отдельный план восстановления.

Документация провайдера: https://timeweb.cloud/docs/apps/deploying-with-dockerfile.
